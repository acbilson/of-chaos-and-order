**A personal DevOps pipeline should start with the system you actually
operate, not the platform you are tempted to learn. Architecture improves
when each new tool earns its operational cost.**

When my Raspberry Pi arrived, I wanted to know how far I could push a
small self-hosted environment. At first, the system was simple: a static
site generated by Hugo and served by Nginx. That was enough to learn the
basic deployment path, but it did not take long for the site to become a
small platform rather than a single static artifact.

I wanted to publish content from anywhere, including times when I did not
have network access. I wanted to add services around the site, such as a
small data-publishing tool with [Datasette](https://github.com/simonw/datasette).
I also wanted the configuration to survive a failed SD card or a server
move. That pushed the project from "host a site" toward "own a repeatable
deployment system."

The first serious improvement was Ansible. I had been comfortable
tinkering directly on the server, but manual configuration does not age
well. It becomes hard to reproduce, hard to audit, and easy to fear. Once
I began securing services under distinct nonroot users, the repeated
user, group, permission, and service setup made the value of
infrastructure as code obvious.

{{< aside >}}
If Ansible is managing server configuration, direct manual edits should
be exceptional. Mixing manual changes with automated configuration makes
the next playbook run feel dangerous, because no one is fully sure which
source of truth will win.
{{< /aside >}}

## The Existing System

Before reaching for containers, the system already had several useful
properties. Nginx handled ingress. Linux services were stable. Ansible
documented and reproduced configuration. Individual processes could be
secured, logged, restarted, and backed up with ordinary Linux tooling.

That matters because architectural decisions should begin with the
current system's strengths, not only its annoyances. The existing setup
was not glamorous, but it was understandable. I could SSH into the
machine, inspect services, read logs, change Ansible roles, and recover
the system without a separate control plane.

The weakness was deployment. As more services accumulated, I wanted a
cleaner path for updating code and content. Containers seemed like the
obvious next step, and Kubernetes, especially [k3s](https://k3s.io/),
was attractive because it promised a modern container model on small
hardware.

## The Kubernetes Temptation

Kubernetes was tempting for good reasons. It would give me practice with
production-style orchestration. It would make services feel more
portable. It would create a path toward image-based deployment rather
than hand-managed process updates. For a team running many services,
those benefits can be substantial.

But the moment I mapped my actual workflow, a hidden assumption appeared.
I had been thinking of the site as one production deployment. In reality,
there were two different concerns: production services and the CI/CD
process that updates those services.

That distinction matters. If a webhook service receives a content update,
builds a new static site, and replaces the running site, then the build
process needs authority over production artifacts. In a container
cluster, that begins to look like a CI/CD service running inside the same
environment it is responsible to modify. That may be possible, but it is
not automatically simpler.

For larger environments, separating CI/CD and production is normal. A
team may have dedicated runners, registries, deployment credentials,
approval gates, and a separate cluster or platform for build work. That
architecture makes sense when many developers are deploying many
services. It was much harder to justify for a personal Raspberry Pi
stack.

## The CI/CD Boundary

The key realization was that I did not need regular container deployment
for the static content path. If Markdown content is treated more like
data than application code, it can live in persistent storage, be updated
by a publishing workflow, and be rendered on a schedule or by a small
build service. The content does not need to be baked into a new
production image every time I write a note.

That reframing lowered the complexity. Instead of asking, "How do I run
a Kubernetes-based CI/CD system on this machine?" I could ask, "Which
parts of this system actually need image replacement, and which parts
only need durable content and reproducible configuration?"

Those are different questions. The first pulls the architecture toward a
platform. The second keeps attention on the workload.

I still looked at a lightweight container build path with Podman,
Buildah, and Skopeo. At the time, ARM support created enough friction
that the experiment did not seem worth the operational cost for my
personal projects. That changed after Debian 11, when Podman became much
easier to run on my 32-bit ARMv7 Raspberry Pi. But the broader lesson
remained: a tool can be technically interesting and still be premature
for the system in front of me.

## A Better Architecture Question

The better architecture question was not, "Can this run on Kubernetes?"
It was, "Which responsibilities should be separated, and what is the
smallest reliable mechanism for each?"

For this environment, the responsibilities were clear:

1. Serve public traffic.
2. Store and update content.
3. Run supporting services.
4. Reproduce server configuration.
5. Build and deploy changed artifacts.
6. Recover from hardware or storage failure.

Ansible already handled configuration and recovery better than manual
server work. Nginx and Linux services already handled traffic and
process management well enough. Persistent content storage reduced the
need for image churn. That left deployment automation as the problem to
solve, not container orchestration as the platform to adopt.

A new platform can be the correct answer, but it should answer a real
operational need. Otherwise it creates a second system to operate before
the first system has outgrown its current tools.

## Conclusion

At this stage, a full container CI/CD architecture required more
machinery than the problem justified. I did not need a dedicated build
node, a Kubernetes control plane, and a production cluster to keep a
personal site and a few small services reliable. I needed reproducible
configuration, clear process boundaries, and a deployment path I could
understand when it broke.

The next step was not Kubernetes. It was a smaller container strategy
with Podman, then eventually a tiny CI/CD pipeline built from Git, Redis,
Podman, and systemd. That sequence was less impressive on paper and more
appropriate for the system.

The lesson is portable: do not let the shape of an admired platform
define the shape of a small system too early. Start with the work the
system has to do. Name the boundaries. Preserve the strengths of the
current design. Add orchestration only when the operational value is
greater than the operational cost.
